# Frayground 项目纲领

> Frayground 为暂定名。本文是项目定位、产品原则、基本概念和范围状态的主要依据。
> 当前阶段：项目初始化与 MVP 验证准备；本文描述目标与约束，不代表相关能力已经实现。
> 最近更新：2026-10-19。

## 1. 项目概览（Project Overview）

Frayground 是一个面向 AI Agent 的开放式游戏与互动平台。玩家可以使用 Prompt、大语言模型、工具、记忆、传统算法或自定义代码构建 Agent，让它们在平台维护的共同规则下进行对抗、合作、竞争和探索。

**玩家设计智能，Agent 执行决策，平台维护世界与裁决结果。**

平台提供环境、规则和权威状态，按权限分发观察，接收结构化行动，校验并结算结果，推进游戏并记录过程。玩家通过观察和复盘改进自己的 Agent。

近期从 Battle，即 AI Agent 对战开始验证。项目的长期定位不局限于单一棋类、机器人战斗或模型排行榜。

## 2. 项目使命（Mission）

让人类能够构建、观察并持续改进自主 Agent，使不同 Agent 在共同规则下产生有意义、值得观看和反复参与的互动。

使命回答项目为什么存在，服务于玩家创作与互动体验，不依赖某款游戏、某家模型供应商或某种 Agent 实现。

## 3. 长期愿景（Vision）

形成一个开放的游戏与互动平台：不同技术实现、不同运行环境的 Agent，可以通过统一的参与约定进入多样的游戏世界；玩家能够理解行为差异、探索策略并持续创造新的互动方式。

愿景描述长期希望到达的产品状态，不是功能排期。支持多样游戏、玩家自主运行 Agent 和开放接入是长期方向；具体协议、工具和交付时机需要逐步验证。

## 4. 核心体验（Core Experience）

玩家的基本循环是：

1. 设计或调整 Agent 的 Prompt、策略或其他决策要素。
2. 让 Agent 进入符合共同规则的游戏环境。
3. 观察它收到什么游戏信息、提交什么行动，以及平台执行后的结果。
4. 通过记录与复盘理解行为差异。
5. 形成新的策略假设，调整并再次参与。

玩家不必亲自操作每一步，Agent 应自主选择行动。平台应让行动和结果可理解，但不要求采集或展示 Agent 的内部推理。

持续可玩性来自策略创造、Agent 之间的互动及改进过程。自动完成一局游戏是闭环的起点，不能单独证明产品价值。

## 6. 产品哲学（Product Philosophy）

本节均为**已确认原则**。

### 6.1 必要规则创造丰富策略

优先以有限、清晰、可组合的规则创造策略空间。游戏定义行动边界，Agent 选择策略；不同决策、信息差异和环境变化共同产生玩法。

Robocode、Screeps、Battlecode 等是理念参考，不是必须复制的功能清单。平台不应依靠预先编写大量角色行为制造全部趣味。

首个游戏保持简单，有利于验证闭环；长期允许复杂游戏。规则复杂度应服务于可理解的策略空间，而不是成为目的。

### 6.2 Prompt 应有可观察的玩法价值

对于使用 Prompt 的 Agent，玩家应有机会通过修改 Prompt 影响策略、风险偏好、合作倾向或具体行动。平台应提供行动反馈和比较依据。

Prompt 修改能否产生稳定、可感知的影响，需要实验检验；不得保证每次修改改善胜率，也不得仅凭单局结果宣称某种 Prompt 更优。

### 6.3 Agent 技术中立

Agent 可以基于 LLM、多模型协作、工具和 MCP、规则程序、搜索算法、本地模型或远程 API。Prompt 不是所有 Agent 的必需组成部分。

参与边界应建立在合法观察与结构化行动上，不能绑定某家模型供应商或某种内部决策方法。

### 6.4 平台是权威裁判

合法动作、资源变化、行动顺序、评分和结束条件由明确的游戏规则控制。原则上不依赖另一套 LLM 主观决定比赛结果。

区分自由表达、结构化行动和客观状态转换。表达本身不能直接修改权威世界状态；即使未来允许自然语言互动，状态变化仍须进入可验证的规则路径。

### 6.5 玩家控制 Agent，信息按权限可见

长期允许玩家选择和维护 Prompt、模型、凭据、工具、记忆及运行环境。平台只交换参与游戏所必需的信息，不以强制托管全部 Agent 为前提。

私有 Prompt、内部推理、凭据和私有记忆不默认向对手或观众公开。观察权限属于游戏规则及产品边界的一部分。

### 6.6 观察、复盘与实验属于核心体验

平台既要让 Agent 能行动，也要让人理解它做了什么。依据实际实验判断玩法与产品价值，避免以演示效果或模型排名替代玩家体验验证。

## 7. 基本概念（Key Concepts）

以下定义固定语义，不规定类名、接口字段或存储模型。

| 概念 | 定义与边界 |
| --- | --- |
| Player | 设计、配置或运营 Agent 的人类用户。一个 Player 可以控制多个 Agent，不要求亲自提交每步行动。 |
| Agent | 根据合法观察自主选择并提交行动的决策实体，不等同于模型、Prompt 或平台账号。 |
| Agent Runtime | 执行 Agent 决策流程的机制，可运行于平台、本地或外部服务；与游戏规则分工不同。 |
| Prompt | 塑造部分 Agent 行为的指令配置，不是完整 Agent，也不是所有 Agent 的必要部分。 |
| GameDefinition | 一类游戏的规则定义，包括状态、观察、动作、状态转换、结算和结束条件。 |
| Game | 某个 GameDefinition 的一次实际运行，正文也称“一局游戏”。 |
| Room | 组织参与者、配置和游戏运行的会话容器。Room 不等同于一局游戏，也不在概念上绑定两人。 |
| 参与席位 | Agent 在某局游戏中的位置或角色。Player、Agent 与执子方等席位概念不能混用。 |
| 权威世界状态 | 平台根据游戏规则维护的真实游戏状态；单个 Agent 的观察可能仅包含其中一部分。 |
| GameObservation | 平台提供给指定 Agent、符合其可见权限的游戏信息。 |
| GameAction | Agent 提交的结构化行动请求；提交不代表已合法或已执行。 |
| Action Schema | 对应游戏允许的行动数据形式；满足结构要求不代表当前状态下行动合法。 |
| Action Validation | 检查行动结构、参与资格及当前规则条件等是否合法的过程。 |
| Decision Record | 一次决策的必要记录，可关联观察、配置版本、提交行动、调用状态和执行结果；不等同于内部推理。 |
| Game Event | 平台记录的客观游戏事件；完整内部记录不意味着所有参与者都能读取其全部内容。 |
| Replay | 依据已记录事实展示或重建游戏进程的能力，不需要重新调用模型决策。 |
| Agent Memory | Agent 为后续决策保留或整理的信息，可能包含主观判断，不等同于平台的客观历史。 |

MVP 默认由同一操作者配置双方 Agent，用作策略实验台。两个 Agent 不意味着必须有两个账号或两个人类 Player；该默认也不代表多人环境中的私有信息应相互公开。

## 8. Agent 所有权与运行方式（Agent Ownership）

**已确认原则：** 玩家保有对 Agent 组成及运行方式的选择和控制。Agent 所有权、托管位置和数据可见性是三个不同问题。

长期允许玩家自行维护模型 API Key、Prompt、决策代码、工具、记忆和运行环境。这些内容不必全部上传平台；本地客户端或自行部署的服务可以只交换必要的观察、动作和结果。

**当前方案：** MVP 可以由平台执行模型调用，以降低闭环验证成本。这不构成未来强制托管的承诺，也不要求第一版完成外部 Agent 接入。

认证、复杂 Key 管理和完整安全体系暂不作为核心交付，但不得要求将长期敏感凭据公开暴露给其他玩家。具体凭据配置方式在实现任务中明确，不在本纲领规定。

## 9. 平台职责与裁判边界（Platform Responsibilities）

**已确认原则：** 平台负责以下职责：

1. 提供游戏环境及共同规则。
2. 维护权威世界状态。
3. 按权限生成并分发观察。
4. 接收符合对应游戏约定的结构化行动请求。
5. 验证合法性，按规则计算结果。
6. 推进行动阶段或回合，判定结束、胜负或评分。
7. 记录必要事件和决策结果，支持观察与回放。

Agent 负责依据观察选择行动。平台不会因为 Agent 的自然语言声称“获胜”或“已获得资源”就认可其状态变化。

模型输出错误、超时和非法动作应作为明确状态被观察，不能伪装成已成功执行。如何重试、判负或终止属于具体游戏与运行策略，实施前决定，不能由临时隐藏逻辑替代。

规则可确定执行与模型决策可复现是不同性质。回放依据实际发生的记录；重新调用模型可能得到不同结果。

## 10. MVP 定位与范围（MVP Positioning）

### 10.1 验证目标

第一版是技术与玩法验证版本，验证以下闭环能否成立：玩家调整策略配置，Agent 根据观察决策，平台执行合法行动，人类能够理解结果并再次尝试。

### 10.2 当前优先方案

- 单个平台实例，一个 1v1 房间，两个 AI Agent。
- 一个简单的回合制棋盘游戏，MVP 选择四子棋作为验证载体。
- 页面左右展示双方 Agent 的 Prompt 编辑区，中间展示棋盘。
- 支持编辑和应用 Prompt，按第 11 节的版本边界生效。
- 支持开始、暂停、单步、继续和重置；采用决策边界暂停，当前决策完成后停住，单步不累积许可；中止当前决策为独立命令。
- 支持观察回合过程、有效行动、错误状态和游戏结果。
- 使用 JSON 等结构化形式提交动作，由服务端校验、更新状态和判定胜负。
- 在本地数据库保留完整客观比赛历史和必要决策记录，支持历史局与逐步回放；重置创建新局并保留旧记录，无自动清理，不承诺云端永久保存或完整实验平台。
- 优先保证完整闭环和可观察性。

当前技术方案为 Java / Spring Boot 核心服务端、MyBatis-Plus、MySQL 8.4 LTS、React / TypeScript 前端和模块化单体。数据库维护完整 schema.sql 和 data.sql，仅空数据卷首次初始化；不使用 Flyway/Liquibase 自动迁移。具体版本与依赖见[系统架构](02-architecture.md)，维护与恢复见[持久化设计](05-persistence.md)。游戏规则与 Agent Runtime 解耦，为后续游戏和房间扩展保留清楚的职责边界。

模型接入选择 DeepSeek Flash 作为 MVP 默认模型，通过独立适配器隔离，不构成平台架构的永久前提。采用单次调用限制与用量记录，不建设金额预算系统。

### 10.3 本阶段不承诺

完整多人房间系统、多游戏平台、动态插件市场、全部 SDK 或协议适配、跨局长期记忆、复杂账号和 Key 管理、永久回放服务、批量对照实验、排行榜及分布式基础设施，均不因本文提及而进入 MVP。

当前选择服务于验证，不应把两个席位、交替行动、完全信息棋盘或平台内调用模型写成所有游戏必须遵守的规则。

## 11. Prompt、上下文与记忆

### 11.1 Prompt 发布边界

**当前方案：** 编辑稿与已发布 Prompt 分离。点击应用后形成新的已发布版本；每次 Agent 决策开始时固定所使用的版本。

新版本从下一次尚未开始的 Agent 决策生效，不能改变已经开始的决策。同一局允许分阶段使用不同版本，因此记录应能关联每次决策实际采用的版本。如何保存版本内容及向谁展示，仍须遵守权限边界。

### 11.2 近期上下文范围

**当前方案：** MVP 使用 STATELESS Decision Context，只根据当前合法观察和已绑定的 Prompt 等必要配置独立构造输入，不自动追加此前模型对话或默认历史，不提供跨局持久记忆。有限历史和策略记忆只保留扩展边界，采用前另行明确长度、预算和权限。

当前棋盘及规则必需的状态不算长期记忆。不得将“无长期记忆”解释为剥夺 Agent 执行合法决策所需的信息。

### 11.3 长期记忆方向

**未来探索：** 最近 N 轮历史、事件摘要、对手策略观察、上轮自身决策与结果、长期关系记忆，以及玩家维护的外部记忆系统。

平台应区分客观历史和 Agent 主观记忆，不将某个 Agent 的猜测直接视为世界事实，也不默认共享其私有记忆。

## 12. 可观察性、决策记录与回放

**已确认原则：** 人类应能理解 Agent 的行动及其执行结果。记录和界面必须区分已提交、已接受、已拒绝及已执行等事实，避免把意图误当结果。

**当前方案：** MVP 在本地 MySQL 保存客观历史、快照及关联决策、Prompt/配置版本、提交行动、校验结果、耗时与可获得的用量；支持历史局及逐步回放。回放以记录为依据，不重新请求模型。私有审计和游戏可见历史分开投影；详细格式见[持久化](05-persistence.md)与[协议设计](10-agent-protocol-and-memory.md)。

这不要求记录内部推理，也不承诺云端永久保存、导出或完整时间轴工具。本地记录无自动清理，备份由操作者负责。可选的行动解释不能替代客观执行记录。

**未来探索：** 版本化 Prompt 的管理界面、同局势比较、关键动作解释、行动统计、模型与策略评估、多局对照实验。

实验比较应说明模型、配置、上下文、先后手及必要的时间或成本条件。一次胜负不足以证明因果关系；开放接入也不自动意味着所有 Agent 获得相同资源条件。

## 13. 扩展原则（Extensibility Principles）

本节是**已确认的长期方向与设计约束**，不要求第一版实现全部能力。

- **房间不绑定两人。** 不同游戏可以有不同人数、角色和观察权限，房间状态应相互独立。
- **行动方式由游戏决定。** 允许未来采用轮流行动、同时提交统一结算等方式，不能把四子棋的节奏当作平台通则。
- **游戏定义可以变化。** 新游戏可以拥有不同状态、动作、观察、评分、结束条件和前端视图。
- **规则与决策分别负责。** 更换 Agent 内部实现不应改写游戏裁判规则，更换游戏也不应要求重建整个平台。
- **参与约定与运行环境分离。** 平台需要理解合法观察和动作，无需理解每个 Agent 的全部内部机制。
- **按证据扩展。** 当前通过清晰边界承接扩展方向；只有实际需求出现时才引入相应基础设施。

这里的统一参与约定不表示所有游戏共用完全相同的动作字段，也不提前决定最终传输协议。

## 14. 未来游戏与开放接入方向

以下全部为**未来探索**，没有默认实施顺序或交付日期。

| 方向 | 可能探索的互动 |
| --- | --- |
| Battle / Robot Combat | 策略对抗与机器人战斗 |
| Coalition | 结盟、合作与竞争 |
| Tragedy | 公共资源困境与群体决策 |
| Negotiation | 谈判与利益交换 |
| Survival | 资源管理与生存 |
| Social Deduction | 社交推理、欺骗与信任 |

开放接入候选包括 Java、TypeScript、Python SDK，HTTP API、MCP Adapter 和可能的 A2A 集成；运行位置可以是本地，也可以是玩家部署在 Cloudflare、Vercel 或 VPS 等环境中的服务。

这些是运行环境解耦的例子，不是已确认兼容性声明。实施前仍需明确接入需求、权限、可靠性和适用条件。

## 15. 非目标（Non-Goals）

### 15.1 当前产品定位不追求

1. 训练通用基础模型。
2. 创造替代现有生态的通用 AI Agent 开发框架。
3. 依靠大量预先设计的复杂规则覆盖所有策略。
4. 绑定单一模型供应商。
5. 强制所有用户 Agent 托管在平台服务端。
6. 将排行榜或模型 Benchmark 作为唯一产品目的。

### 15.2 第一阶段不追求

1. 将第一版做成 MMORPG。
2. 一开始建设完整微服务和分布式系统。
3. 为尚未验证的未来功能提前实现复杂基础设施。

阶段性非目标不是永久禁止探索；长期定位变化则需要按第 19 节明确决策。原型中未实现某项长期能力，不等于取消这一方向。

## 16. 成功标准（Success Criteria）

| 层次 | 要回答的问题 | 可采用的证据 |
| --- | --- | --- |
| MVP 闭环 | 能否从配置、决策、合法行动执行走到结束与重置？ | 完整对局、控制操作、错误状态和终局检查 |
| 行为可观察 | 玩家能否理解实际行动、结果及 Prompt 生效版本？ | 对局记录、复盘核对与体验反馈 |
| 策略实验 | Prompt 或决策配置变化是否有机会产生可感知差异？ | 相同或可比较局势、多次试验及差异记录 |
| 持续参与 | 玩家是否愿意再次调整、观看并重复参与？ | 真实使用中的重复试验、反馈及参与行为 |

前两层用于近期交付验收；后两层需要产品实验，不能由工程检查代替。观测指标、样本量和判断阈值应在具体实验前约定，本文不虚构基线或收益。

如果闭环正常但玩家缺少改进意愿，或互动缺乏可理解差异，应重新检查游戏选择、反馈方式或玩家体验，而不是仅增加基础设施。

## 17. 关键假设与验证方式

本节全部为**待验证假设**。

| 假设 | 验证方式 | 反证信号与调整方向 |
| --- | --- | --- |
| 四子棋适合作为首个验证载体 | 测试闭环、可理解性及不同配置的行动差异 | 若策略表达长期受限，可更换验证游戏；不据此取消平台使命 |
| Prompt 能产生可观察的行为差异 | 在可比较局势下重复比较不同 Prompt，控制或记录模型和上下文条件 | 若差异不稳定或被随机性掩盖，检查任务、指令与实验设计，不宣称已证明玩法价值 |
| 回合过程和复盘能帮助玩家改进 | 观察玩家是否能解释行为并据此提出新策略 | 若只能看懂胜负，改进反馈与记录呈现 |
| 单房间双 Agent 足以验证早期体验 | 邀请目标用户使用并观察是否形成调整循环 | 若关键互动依赖更多参与者，提出下一阶段范围决策 |
| 低成本兼容模型 API 能满足原型 | 检查行动合法率、延迟、稳定性和费用 | 若不满足，调整模型或决策方案；不改变技术中立原则 |
| 当前观察或有限历史足够支撑首个游戏 | 检查合法决策与行为是否受信息缺失影响 | 若不足，明确加入必要历史，避免直接升级为复杂长期记忆系统 |

实验未达预期应保留事实和条件。假设被推翻不自动授权扩大 MVP，也不应被解释为需要更复杂的架构。

## 18. 开放问题（Open Questions）

2026-10-19 架构设计阶段已确认部分问题；确认方案不代表已经实现或验证。

| 问题 | 当前状态与决定 | 后续时机 |
| --- | --- | --- |
| 暂停、单步、重置 | 已确认：决策边界暂停；单步执行一个 Agent 的决策及结算，不累积许可；独立中止当前决策；重置隔离旧 Match | 实现前按[状态机](03-domain-model.md)设计竞争测试 |
| 非法动作、超时、模型失败 | 已确认：展示错误并暂停，不自动重新生成、不替选动作或判负；人工继续创建新 Decision | 实现 Agent 调用与恢复测试 |
| 首个游戏、模型与费用边界 | 已确认：四子棋、DeepSeek Flash 默认适配；限制单次调用并展示用量，不建设金额硬预算 | 精确供应商能力与实际调用仍需集成验证 |
| 当前观察与历史 | 已确认：STATELESS，无默认历史追加；其他记忆模式延后 | 实现 ContextBuilder 时验证隔离 |
| 保留与复盘 | 已确认：本地完整客观历史与必要审计；无自动清理；重置保留旧局，最小逐步回放；重启恢复后暂停 | 数据库与回放实施验收 |
| 模型凭据 | 已确认：后端环境变量配置，前端和记录不包含真实凭据；默认本机实验室 | 真实模型接入前检查脱敏与配置 |
| 精确依赖与镜像兼容性 | 待验证：技术版本基线已定，数据库镜像补丁/摘要与依赖解析未实测 | 工程骨架阶段，不静默换栈 |
| 早期玩家、实验条件与成功阈值 | 仍待决定 | 开始产品验证前 |

远程身份授权、多人同时回合缺席规则和策略记忆细节仍是未来实施前的开放问题，不因接口草案而进入 MVP。决定理由与重新评估条件见[ADR](09-architecture-decisions.md)。未决事项不能在实现中用未经说明的默认值悄悄关闭。

## 19. 文档演进与重大变更

### 19.1 内容与职责

本文维护产品事实与范围状态；AGENTS 维护开发协作约束；README 维护外部简介和导航。摘要可以重复核心句，但详细定义、未来方向和假设以本文为主，避免多份完整副本。

术语或链接修正可直接修订。当前方案变化需说明理由和影响，并同步受影响的摘要。实验结论需注明条件和证据，保留原问题及结论演变。

### 19.2 重大产品与架构决策

改变使命、核心职责边界、Agent 所有权、技术中立、私有信息原则或开放方向，均属于重大产品变化，应先形成明确记录，经项目负责人确认后更新相关文档。

重要架构选择使用 ADR；产品定位变化使用产品决策记录。首次发生此类决定时，按需建立 docs/decisions/，无需提前创建空体系。

记录至少包含：日期、类型、状态、背景、选项、决定、理由、影响、重新评估条件，以及取代或被取代关系。采用提议、已采纳、已否决、已被取代等明确状态。Git 历史可以补充变更轨迹，不能替代决策理由。

### 19.3 实施与创新

开发任务应先识别所依据的原则、当前范围和待决问题。重大冲突先提出具体选择，不能通过普通功能变更隐式修改纲领。

新增游戏、Agent 技术或互动形式，只要符合使命与核心边界，就可以提出实验。实验结果可以推翻当前方案和假设；进入正式实施前再明确范围，不把探索自动升级为交付承诺。

纲领保留目的、语义和边界。Java 类、数据库结构、API、部署拓扑、具体 SDK 与任务拆分，放入对应的设计或实施文档。
